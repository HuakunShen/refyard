## Follow-up: secure Windows provider storage design

### Existing implementation and boundary

- The Node store is `packages/host-node/src/provider/manager.ts:71-75, 123-148`: it owns JSON serialization, validation, and memory caching; `load()` currently calls `readFile` directly, `set()` writes directly to the final path, and `remove()` unlinks it. Its interface is a local TypeScript `ProviderStore`, not a shared Git contract (`:63-69`).
- The Rust host already has the right Windows primitives in `crates/refyard-host/src/jobs/windows_acl.rs`. `create_private_file_handle` supplies the current-user owner and protected DACL to `CreateFileW(CREATE_NEW)` before the file exists (`:326-374`); `verify` reads back the owner and requires a protected DACL with exactly the expected user and SYSTEM ACEs (`:377-485`); `create_private_temporary_file` exposes private creation (`:627-641`), and `open_private_file_for_read` validates/repairs the existing ACL before opening a data reader (`:643-659`). `secure_private_directory` validates/restricts a directory (`:488-500`).
- These are **not currently callable by Node**: the ACL module is `pub(crate)` under `crates/refyard-host/src/jobs/mod.rs:20-21`, and the relevant functions are `pub(crate)` or `pub(super)`, not exported over a process or FFI boundary. `refyard-host` is linked by the Rust CLI, optional HTTP adapter, and Tauri app; it is not a Node dependency (`crates/refyard-host/src/lib.rs:1-7`). The `refyard-native` executable currently exposes doctor/serve/open only (`crates/refyard-cli/src/main.rs:14-62`). Repository search found no N-API/Neon binding. Tauri invoke is a separate desktop UI boundary (`apps/desktop/src-tauri/src/commands.rs:298-393`, `packages/backend-tauri/src/adapter.ts:240-255`), and does not serve the Node HTTP/CLI host.
- The Node host's root resolver merely calls `mkdir(..., {mode: 0700})` (`packages/host-node/src/registry/roots.ts:203-207`); on Windows that is not proof of a private directory. The provider directory must therefore get an actual ACL policy too, since Windows controls delete/replace rights at the parent directory.

### Closest predecessor analogue

The read-only CrossCopy source has no direct Refyard-style provider-connection store. Its closest local-secret analogue is `CrossCopy/packages/crosscopy-control-api/src/transport.rs:402-420, 423-469`: it creates the Windows state directory and file with an explicit current-user/SYSTEM SDDL, then reads the security descriptor back and rejects a mismatch. The comments at `:452-469` explain why both objects matter: the directory DACL governs whether the file can be replaced. This is relevant policy precedent, not a provider-store implementation to copy wholesale. CrossCopy's endpoint-key file helper (`packages/crosscopy-fabric/src/identity/device_key.rs:111-133, 180-197, 199-223`) sets Unix modes but deliberately does not implement a Windows ACL; it is not sufficient precedent for Windows provider secrets.

### Recommendation

Smallest design that reuses the proven ACL implementation and preserves the Node/Rust product boundary: add a narrow, Windows-only private-state operation to the existing first-party `refyard-native` executable, backed by these Rust ACL primitives, and have `packages/host-node` call it through a fixed executable path/argument set. Keep JSON/schema/cache/provider logic in TypeScript. Send secret bytes only over the child's stdin (never argv, environment, or logs); return loaded bytes only over captured stdout; make diagnostics secret-free. Operations should be limited to secure-directory preparation, private create/replace/read, and removal. Preserve POSIX `0700`/`0600` handling in the Node filesystem adapter on Unix. The Windows ACL should match the established current-user plus LocalSystem policy, without broad inherited principals.

For writes, use a private temporary file created with the ACL at `CREATE_NEW`, write and flush it, then atomically replace the destination from within the helper; do not create a normally inherited file containing a token and tighten it afterward. For reads, validate the file's owner/type/DACL through the handle before returning bytes. On directory creation/reuse, validate the directory DACL first. Do not treat `stat.mode`, successful `writeFile`, or an ACL repair performed after secret bytes are written as proof of privacy. This is a recommendation, not an implemented or reviewed architecture decision; it requires confirming how the Node product locates and packages the Windows helper before code is written.

### Focused evidence to require in implementation

- Rust Windows tests: create a fresh directory/file and independently read back owner SID, protected DACL, and exact allowed ACE set; reject reparse/non-regular files; show that an unexpected inherited or extra ACE is refused or repaired according to the existing `windows_acl` policy. Existing ACL oracle coverage is in `crates/refyard-host/tests/support/windows_acl.rs:99-169` and `crates/refyard-host/tests/embed.rs:1213-1305`.
- Node store tests on Windows: provider connect writes a file whose directory and file ACLs satisfy the current-user plus LocalSystem contract; a fresh store can load it; replacement preserves the contract; removal works; malformed data still fails closed; deliberately loosened ACLs do not silently expose/use the token. Assert ACL facts through an independent Windows security-descriptor inspection, not POSIX mode bits.
- Keep the current Unix mode assertions and add/retain checks for directory `0700`, file `0600`, round-trip, removal, corrupt-file refusal, and no-token-in-results on Unix. Run both focused store tests and provider integration tests on Windows and Unix.

### Unresolved assumptions

The repository does not yet establish that `refyard-native` is installed beside every Node CLI/service deployment, or that adding a helper operation to that binary is acceptable for the Node-only browser forms. The recommendation depends on that packaging decision. If a helper executable cannot be shipped, the alternative is a separately reviewed Windows native-binding boundary; neither a binding nor a system PowerShell/`icacls` fallback exists in the current code. The exact replacement atomicity and concurrent writer behavior should be specified before implementation; the current Node store writes the final path directly and does not serialize concurrent set/remove operations.
