# 2026-09-26 13:49 SGT — Xross Refyard view entry

## Core decision

Ship a dedicated Refyard view for Xross's typed native facade, with a local pack and a separate hosted output. Keep the browser/HTTP and Tauri sessions independent of this view.

## Options considered

- Adapting `BackendSession` would require inventing local execution targets, paths, and operation records that the Xross contract does not provide.
- Correlating a lost submission response with recovery by resource label, time, or list order would be ambiguous when two previews have the same label.
- Treating a terminal job state as permission to write would miss missing durable observation, a stale target snapshot, or another exact-resource blocker.

## Decision and rationale

The view consumes only `window.xrossRefyardV1` and correlates a preview with recovery only by output-only `recoveryId`. A row offers a new-preview affordance only when the native-computed `writeFence` is `released`; native preview admission still makes the final decision. Unknown outcomes remain unknown, and the UI points to Xross Repositories Recovery without exposing owner actions or replaying Submit.
