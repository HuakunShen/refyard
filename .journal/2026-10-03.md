# Project Journal — 2026-10-03

## 16:05 Desktop pairing: the embedded panel was leaving the renderer's transport

- **Core Decision/Topic**:
  - The DeepSeek Harness plugin showed `Unauthenticated: InternalError: the workbench hit an
    unexpected failure and cannot describe it` in the desktop app while the same panel paired
    correctly in a browser. Fix the transport so the panel works in both, without relaxing any
    authentication, CSP or CORS rule.

- **Options Considered**:
  - *Where the API address comes from*:
    - Option A: Keep the absolute HTTP address (`http://127.0.0.1:<port>/refyard`) and widen the
      desktop CSP / allow the HTTP origin. Discarded: the desktop renderer's origin is
      `dsh-app://app`, so its `connect-src 'self'` refuses the request before it reaches the
      service, and the shell's forwarder had already answered a live desktop-origin preflight
      with `403 that origin is not one this service was started for`. Widening would have meant
      adding an origin and a scheme to Refyard's own policy for the embedder's convenience.
    - Option B: Serve a **root-relative** mount (`api=/refyard`), so the SPA keeps whatever
      transport carried it — HTTP in a browser, `dsh-app://app` in the desktop shell.
    - *Choice*: Option B. `normalizeBaseUrl` accepts a root-relative mount and rejects the forms
      that can escape it (network paths `//`, backslashes, raw or percent-encoded dot segments,
      control characters), because a `fetch` resolves those before dispatching.
  - *The missing `Origin` on the desktop carrier*:
    - Option A: Relax ticket-origin binding. Discarded: tickets are bound to the origin they were
      minted for on purpose.
    - Option B: Restore a missing `Origin` in the plugin's proxy, **after** the route's own
      Origin/Host/Fetch-Site policy has passed, using the origin derived from the already
      validated HTTP `Host`.
    - *Choice*: Option B. Explicit origins pass through unchanged; foreign, opaque and
      origin-less cross-site requests are refused before the mapping, and bearer/ticket checks
      stay upstream.

- **Final Decision & Rationale**:
  - The panel is one SPA in two carriers, so the address it is given must be relative to the
    carrier rather than to the machine. That is also why nothing else had to change: the
    embedded service, the single-use ticket, the bearer session and the origin policy are
    unchanged.

- **Key Changes Made**:
  1. `integrations/dsh/src/host.ts`: the pairing redirect writes `api=/refyard`; the proxy
     restores a missing `Origin` from the checked HTTP authority after the policy check.
  2. `apps/web/src/lib/connection.ts`: `normalizeBaseUrl` accepts a safe root-relative mount
     (and normalises `/` to no prefix), rejecting the escaping forms above. An explicit
     `?api=` keeps winning over a stale stored HTTP address.
  3. `tests/unit/connection.test.ts`, `tests/integration/dsh-plugin.test.ts` (new): the two
     regressions were written first and failed for the right reason (absolute API in the
     redirect, 403 on the origin-less exchange, stale stored address winning). The security
     cases use raw Node `http.request` because `fetch` normalises `Host`/`Sec-Fetch-Site`.
  4. `docs/evidence/2026-10-03-dsh-desktop-pairing.md`: the evidence record.
  5. Verified: 85 files / 803 tests, `tsc --noEmit`, `check:boundaries`, `pnpm build:dsh`, a
     Chromium run against a separate `web` profile, an Electron 40.4.1 window driving the
     installed shell's forwarding semantics, and finally the user's own installed desktop
     window. Commits `c23335b`, `4d9bc3c`.

- **Future Considerations**:
  - The host half is imported once per Harness process and cached by package name, so every fix
    to it costs the user a full restart. Two known cosmetic errors remain on the panel
    (`/host/capabilities` 404, provider pull-requests 409); neither is a pairing failure.

## 17:40 Publishing: `dsh-plugin-refyard` gets the npm line the sibling plugin already has

- **Core Decision/Topic**:
  - `dsh-plugin-refyard` has never been published (`npm view` answers 404). Add the release
    path, following `dsh-plugin-spacelens` in `~/Dev/space-lens`, which publishes on a tag push
    with npm trusted publishing and a public provenance attestation.

- **Options Considered**:
  - *Tag namespace*: reuse `v*` (taken by the CLI/service package) or `app-v*` (taken by the
    desktop release)? Discarded both: one tag must name one artifact.
    *Choice*: `plugin-v*`, with a workflow that checks the tag against
    `integrations/dsh/package.json` before building anything.
  - *Auth*: an `NPM_TOKEN` secret, or OIDC? *Choice*: OIDC with `environment: npm` and
    `id-token: write`. No long-lived secret to rotate, and provenance comes for free.
  - *Where the build runs*: a CI-only recipe, or the manifest's own `prepublishOnly`?
    *Choice*: `prepublishOnly`, so a local publish and a CI publish produce the same bytes from
    the same command.

- **Final Decision & Rationale**:
  - Trusted-publisher settings live in the settings of a package that already exists, so the
    **first** version cannot be published from CI. The hand-publish is a one-time step; after
    that, releases are tags. The repository has no `NPM_TOKEN` secret and no `npm` environment,
    so the first publish was authorized interactively instead: `npm login` on this machine plus
    a one-time password on the publish itself.

- **Key Changes Made**:
  1. `.github/workflows/dsh-plugin.yml` (new): a `bundle` job that builds and `npm pack
     --dry-run`s on pull requests, and a `publish` job gated on `plugin-v*` tags with the
     version check, `environment: npm`, `id-token: write` and
     `npm publish --access public --provenance`.
  2. `integrations/dsh/package.json`: publishable metadata (`repository` with `directory`,
     `homepage`, `bugs`, `keywords`), `private` removed, and `build`/`prepublishOnly` scripts.
  3. `integrations/dsh/LICENSE`: the AGPL text, so the tarball carries the license its manifest
     declares.
  4. `integrations/dsh/README.md`: an `Installing` section and a `Publishing` section that names
     both trusted-publishing traps.

- **Published and verified (17:20)**:
  - `dsh-plugin-refyard@0.1.0` is live: `dist-tags.latest = 0.1.0`, `license: AGPL-3.0-only`,
    `repository.directory: integrations/dsh`.
  - The first attempt failed with `EOTP` — the account requires a one-time password for writes,
    and a non-interactive shell cannot answer the prompt. The manifest's `prepublishOnly` had

    keeps the OTP from expiring during a rebuild.
  - The bytes are the ones that were built: the published tarball, the local tarball and the

  - `npm install dsh-plugin-refyard@0.1.0` in an empty directory installs one package whose
