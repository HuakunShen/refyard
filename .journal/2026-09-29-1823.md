# 2026-09-29 18:23 +08 — Scrub pairing URL before session publication

## Core decision

On a successful HTTP connection from a ticket-bearing page, remove `pair=`
from the address bar before publishing the backend session to the workbench.

## Options considered

- Add a wait to the WebKit E2E assertion. Rejected: the source showed a real
  interval in which the visible workbench could coexist with a credential in
  the URL. Waiting would hide that privacy issue.
- Scrub before attempting connection. Rejected: a dead remembered bearer needs
  the original ticket as fallback, and hosted password failures retain the
  in-memory ticket for retry.
- Scrub only after `pairWorkbenchSession` finishes. Rejected: that was the
  existing order; `connect` calls `onSession` before the session helper's
  `finally` block executes.

## Final decision and rationale

The common `connect` boundary knows the backend connection succeeded and
whether the page loaded with a ticket. It now strips the ticket before
`adopt(connected)` makes the workbench visible. This covers both a freshly
spent ticket and a still-live remembered bearer that did not spend the ticket.
Failed connections still take the previous catch/finally path and preserve
their in-memory retry value.

## Key changes made

Added a real-service integration assertion observing the URL at `onSession`.
It failed with `pair=` before the fix for both fresh pairing and live remembered
bearer, then passed after the fix. The two integration/session files passed
8/8. The exact address-bar E2E passed on all three engines (3/3); the full
read-only spec passed 30/30 across Chromium, Firefox and WebKit. The local
WebKit URL case also passed eight repetitions before the fix, so its Linux CI
occurrence is not called a deterministic local reproduction. Web build and
`svelte-check` passed, with zero errors; reviewer found no P0/P1.
