# Journal — 2026-09-29 04:12 Asia/Singapore

## Core decision/topic

Keep commit-context-menu write actions synchronized with the current busy state
while the menu remains open.

## Options considered

- Extend or retry the invalidation wait: rejected. The canonical Firefox trace
  showed both status and repository-prefix invalidation settling and `busy`
  returning to false; the stale disabled value belonged to the already-open
  menu's action snapshot.
- Close/reopen or remount the menu after writes: rejected. It hides the stale
  snapshot rather than fixing live menu state.
- Build actions once when opening the menu: rejected for actions whose
  `disabled` field depends on reactive `contextDisabled`.

## Final decision & rationale

Keep an action builder while the commit/ref context menu is open and evaluate it
inside a `$derived` scope. This makes the Svelte dependency on `contextDisabled`
observable, so the existing menu updates when a write starts and when its
invalidation finishes. Clear the builder on close to avoid retaining a stale
commit or ref. Preserve the immutable snapshot behavior for closed menus.

The regression gates the real status HTTP response after a real local write; it
does not mock Git or business logic. Playwright's current docs explain that
page/context routes can miss requests owned by a Service Worker. The test alone
uses `serviceWorkers: "block"`, matching existing Refyard specs that need
reliable request interception, and keeps coverage in all three engines.

## Key changes made

- `packages/git-ui/src/components/CommitList.svelte`: derive active commit/ref
  actions while the menu is open and clear the builder on close.
- `tests/e2e/context-menu.spec.ts`: prove disabled → enabled in the already-open
  menu while a real status refresh is held, then finish creating the tag.
