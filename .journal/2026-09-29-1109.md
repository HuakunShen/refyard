## Core decision/topic

Request `FILE_READ_ATTRIBUTES` on every validation handle used with
`GetFileInformationByHandleEx(FileAttributeTagInfo)`. This is an independent
access-mask correction; it does not identify or explain the separate ACE
readback mismatch in hosted Windows run `36514024537`.

## Options considered

- Treat `READ_CONTROL` as sufficient for a handle used to inspect file
  attributes. Rejected: the API contract lists `FILE_READ_ATTRIBUTES`
  separately, and the code was opening existing state and lock files without
  that right.
- Replace the narrow validation masks with `GENERIC_READ` or broader data
  access. Rejected: the ACL/owner validation path only needs the explicit
  attribute right; broadening it would request more than the metadata query
  requires.
- Add only `FILE_READ_ATTRIBUTES` to the directory and existing-file
  validation handles, leaving the private DACL and exact readback policy
  unchanged. Chosen.

## Final decision & rationale

Add the one documented access right at each `CreateFileW`/reopen path that
validates an existing directory, state file, or lock file through
`FileAttributeTagInfo`. The newly created file and final data-reader handles
already request `GENERIC_READ`, which includes this right. Keep the current-user
owner check, protected user/SYSTEM DACL, exact ACE checks, reparse refusal, and
handle-bound reopen behavior unchanged. Do not use this fix to infer or soften
the separate ACE mismatch.
